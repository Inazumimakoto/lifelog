# lifelify の操作遅延と改善結果

2026年10月12日。タブ切り替え、スクロール、カレンダー操作、入力、保存、チェックで共通して負荷を増やす処理を調査し、修正した。特に習慣チェックは、連続達成日ごとに全履歴を検索していたため、長い履歴で処理時間が大きく増えていた。さらにストア全体の更新による画面再計算、同期ごとの予定ID変更、メインスレッドでの写真処理が重なっていた。

## 原因と実装

| 原因 | 操作への影響 | 修正 |
| --- | --- | --- |
| 習慣の連続達成日を数えるたびに全記録を検索し、チェック前後で同じ検索を繰り返す | チェックから触覚フィードバックまでメインスレッドを占有。計算量は履歴数と連続日数の積 | 完了日集合を一度作って再利用。全習慣達成も対象日の完了IDを一度集計 |
| 習慣の履歴辞書を記録ごとに取り出して変更する | Swiftのコピーオンライトで増え続ける内側の辞書を反復コピー | デフォルト添字で辞書をその場で変更。空の曜日設定で終了しない連続日数計算も修正 |
| AppとTabViewの親がAppDataStore全体を監視する | 日記・天気・習慣の変更でも全タブの親へ更新が伝わる | ストアの所有と購読を分離。各ViewModelが必要な入力だけ購読 |
| Todayが全データを一括更新し、Journalが描画中にStateキャッシュを書き換える | メモ編集でも予定・タスクを再計算。不要な再描画とキャッシュ破棄 | Todayの購読を分割し同じ操作の更新を集約。JournalキャッシュをViewModelへ移し、関連する7入力で無効化 |
| EventKitの長期間取得がMainActorで同期実行される | 起動後やカレンダー更新中に操作・描画を待たせる | 専用の直列キューへ移動。同じ期間の同時要求は取得を共有 |
| 外部予定に同期ごとにランダムIDを付ける | 同じ予定でも一覧の要素が置換され、通知と保存も作り直される | カレンダー・元の予定・繰り返しの発生日から安定したIDを生成。同じデータは再公開・JSON保存を省略 |
| 予定1件の編集で全予定を取得し全モデルを更新する | 保存時間が蓄積した予定数に応じて増える | 通常の追加・編集・削除は対象IDだけ取得して保存。一括更新では未変更モデルの代入を省略 |
| 原寸写真を枚数だけでキャッシュし、画像が描画時まで未デコードになる | 写真表示・スクロール時のメモリ圧迫とメインスレッドの画像処理 | 原寸3枚・64 MiB目安、サムネイル32 MiB目安のコスト制限。単体で予算を超える画像は保持せず、メモリ警告時に解放。描画準備は直列ワーカーで実行 |
| サムネイル表示でも原本の識別情報を作り、写真リンク判定も画面上で実行する | 原本読込・ハッシュ・画素比較が入力や画面表示と競合 | 表示に不要な識別処理を省略。インポートとリンク判定を非同期化し、キャンセル・古い結果の反映を防止 |
| HealthKitの独立した取得を直列に実行し、累積クエリの対象期間が無制限 | 取得の待ち時間と読込量が増え、重複した要求も発生 | 5種類を並行取得し期間を限定。同時の更新要求を共有。権限付与後は付与前の取得結果を再利用しない |
| ヘルスの描画ごとに全日付を整列・変換し、日記を各日ごとに全件検索する | グラフ参照のたびに再計算し、ランダムIDで表示要素も置換 | 日付辞書と保存済みの計算結果を利用。点のIDを日付・時刻に固定し、日記本文変更では再集計しない |
| 同じ日記や天気でも公開・保存し、本文保存でも全写真パスを検索する | 編集終了や保存時に不要な更新が広がる | 未変更なら更新を省略。写真パス変更時だけ同期を再設定し、保存失敗後の再試行は保つ |

EventKitの同期取得をバックグラウンドへ移す方針は[Appleの取得ガイド](https://developer.apple.com/documentation/eventkit/retrieving-events-and-reminders)にも沿う。原寸の解像度・写真の識別方式・ユーザー作成の本文や名前は保持する。

## 集計処理の測定

Mac上のSwift最適化ビルド `swiftc -O` で、旧処理と修正後の実装を同じ入力で比較し、返り値の一致も検証した。実機のタップ応答やフレーム時間を測った数値ではない。長期履歴のケースは負荷を確認するための合成データで、利用者の実データ件数を仮定していない。

| 処理と入力 | 修正前 | 修正後 | 条件 |
| --- | ---: | ---: | --- |
| 連続達成日数 20習慣 × 2,000日 計40,000記録 | 2,249.64 ms | 2.61 ms | 3回の中央値。対象習慣は配列末尾、2,000日連続 |
| 全習慣達成の確認 同じ40,000記録 | 37.05 ms | 0.32 ms | 3回の中央値 |
| 習慣履歴の辞書生成 20習慣 × 2,000日 | 413.07 ms | 40.08 ms | 5回の中央値 |
| 習慣履歴の辞書生成 1習慣 × 10,000日 | 479.60 ms | 9.72 ms | 5回の中央値 |
| 日付ラベル1,000個の整形 | 18.92 ms | 0.46 ms | 5回の中央値。出力文字列の一致を確認 |

測定環境はApple arm64 Mac、macOS 26.4.1、Swift 6.2.1。再現コードは[辞書と日付整形](performance/main.swift)と[習慣チェック](performance/habit-completion/main.swift)。リポジトリのルートから実行できる。

```sh
swiftc -O docs/performance/main.swift lifelog/ViewModels/HabitRecordIndex.swift -o /tmp/lifelog-perf
/tmp/lifelog-perf
swiftc -O docs/performance/habit-completion/main.swift lifelog/Services/HabitCompletionQuery.swift -o /tmp/lifelog-habit-perf
/tmp/lifelog-habit-perf
```

## 挙動を保つための確認

回帰テストは、更新通知の範囲、キャッシュの無効化、日付と夏時間、予定の繰り返しID、未変更保存、保存再試行、写真の解像度・メモリ解放・選択競合を対象にする。通知はデータが同じでも予定済みの最初の通知時刻を過ぎたら後続を補充する。ヘルスのキャッシュはタイムゾーン・日付・ロケール変更でも再計算する。

66件の回帰テストを追加し、最終実行は全262件成功、失敗0件、スキップ0件。署名を有効にしたシミュレーターでKeychainを使うE2EEテストも実行した。実機向けReleaseビルドと `git diff --check` も成功した。

```sh
xcodebuild test -project lifelog.xcodeproj -scheme lifelog -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -parallel-testing-enabled NO
xcodebuild -project lifelog.xcodeproj -scheme lifelog -configuration Release -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build
git diff --check
```

iOS 26.1のテストではAppDataStoreとHealthViewModelの解放時にSwiftランタイムのクラッシュを再現した。スタックは[Swift側の報告](https://github.com/swiftlang/swift/issues/88036)と一致しており、既存のShoppingStoreと同じ明示的な `nonisolated deinit {}` で回避した。

## 検証範囲と実機計測

iPhone 17 Proシミュレーター、iOS 26.1、Debug、`-simulator-demo-data` で変更前後の起動と月送りを確認した。15秒のプロセスサンプリングにはUI自動操作のアクセシビリティ処理と待機時間が含まれるため、フレーム落ち率や応答時間の比較には使用していない。Time Profilerの直接接続はこの環境で対象プロセスを取得できなかった。

最終ビルドでもホーム・カレンダー・買い物・習慣・ヘルスの全タブ切り替えとホームのスクロールを確認した。

実機のReleaseでのFPS・入力応答・Todayの1秒要件は別の計測対象となる。特に初期SwiftData読込、習慣の年間ヒートマップ全体の作成、TasksとEventsのセクション抽出は、実データ量に応じて次のプロファイルで確認する対象として残る。今回の数値からアプリ全体が何倍速くなったとは判断しない。
