# 実機の起動遅延調査

2026年10月29日。症状は「実機のiPhoneで、ロゴが表示されたまま長く待つ」。アプリコードは変更せず、コード・履歴の確認、接続中の実機のApp Launch計測、シミュレータでの補助確認を行った。

## 結論

今回の実機計測で最大の待ちは、起動時の「今日の予定・タスク」通知の再登録だった。保存データを初期化するメインスレッドが、既存通知を取り消す `UNUserNotificationCenter.removePendingNotificationRequests(withIdentifiers:)` 内の同期XPC応答待ちで約 **2.45秒** 停止していた。この処理は初回描画より前に実行されるため、その間はiOSの静止ロゴから進めない。

ロゴ演出の設定時間は合計0.53秒で、通信完了を待つ条件はない。ただし初期画面の構築、写真ファイルの走査、ヘルス更新などがメインスレッドを使うため、演出の開始・完了が設定時間より遅れる余地もある。

この通知の取り消し処理は2026年2月10日の `569021b` から存在する。今回の計測で現在のボトルネックは確認できたが、「最近のどの変更から遅くなったか」や、OSの通知サービスの応答が今回遅かった理由は確定していない。

## 実機で確認した内容

- iPhone 12、iOS 26.2、インストール済みlifelify 1.17.0 / build 52。
- Xcode Instruments 26.0のApp Launchテンプレートで実際に起動し、12.42秒を1回記録。Time Profilerはコンテキストスイッチ・待機スレッドも記録する設定。
- DBのコピーで `PRAGMA quick_check` が `ok` となり、整合性を確認できた。
- 通知の対象となる繰り返し予定はなかった。
- 保留中の写真のアップロード・削除はなかった。

### 起動の区間

| Instrumentsの区間 | トレース内の時刻 | 所要時間 |
| --- | --- | ---: |
| プロセス作成 | 0.000–0.404秒 | 0.404秒 |

| `didFinishLaunchingWithOptions()` | 1.670–1.738秒 | 0.067秒 |

一部のシステム初期化区間は重複するため、表の単純合計は起動時間にならない。初回フレームは起動ロゴを含み得るため、5.645秒を「ホームが操作可能になった時刻」とは扱わない。ロゴ解除・操作可能になる瞬間は、この計測だけでは確定していない。計測器の負荷も含む1回の記録であり、日常の起動時間の平均や修正後の改善幅を示す値ではない。

### 最大の待ちを作った呼び出し

```text
AppDataStore.init
  rescheduleTodayOverviewReminderIfNeeded
    NotificationService.scheduleTodayOverviewReminder
      cancelTodayOverviewReminder
        NotificationService.cancel(identifier:)
          UNUserNotificationCenter.removePendingNotificationRequests(withIdentifiers:)
            UNUserNotificationServiceConnection
              xpc_connection_send_message_with_reply_sync
                mach_msg2_trap
```

メインスレッドのこのスタックに約2.445秒のサンプル重みが付いており、2.829秒のscene接続区間の大半を占める。これはCPUで計算し続けた時間ではなく、同期IPCの応答待ちである。

対応するコードは [AppDataStore.swift](../lifelog/Services/AppDataStore.swift) の初期化末尾、[AppDataStore+Notifications.swift](../lifelog/Services/AppDataStore+Notifications.swift) の `rescheduleTodayOverviewReminderIfNeeded`、[NotificationService.swift](../lifelog/Services/NotificationService.swift) の229–243行と284–290行。

先に行われる予定通知の取り消しにも実行サンプルがあり、最初の通知接続の生成だけが原因とは確認できない。同じ今日の通知の取り消しが起動後にもう一度現れた際は約0.52msで、呼び出しのたびに必ず2.45秒かかるわけでもない。

## ほかの処理との比較

- **保存済みヘルスの初期変換:** 約45msのサンプル。`AppDataStore`の初期化内で通知の長い待ち以外に観測した仕事は約0.17秒。全履歴を同期読み込みする構造は改善対象だが、この記録で最も大きい原因ではない。
- **初回フレームの構築:** 約1.05秒。SwiftUIのグラフ・レイアウト、テキスト、型情報、アセット・フォントなど初回の準備が中心。内訳は相互に重なるため合算しない。TodayViewModelの初期化は約10ms。
- **写真同期の設定:** 初回描画区間では約27ms。その後の全写真のファイル確認は2回の走査で約281msのサンプルがあり、約240msが `stat` / `lstat`。描画後の処理も演出と競合し得る。
- **ヘルス更新後の保存:** 初回フレームより後、約7.44–7.57秒付近に約120ms。起動解除がHealthKitの通信完了を待つ構造ではない。
- **Firebase初期化:** `didFinishLaunchingWithOptions()` 全体が約67msで、今回の最大の待ちではない。
- **CloudKit:** SwiftDataのDBは `cloudKitDatabase: .none`。写真のネットワーク同期完了もロゴ解除の条件にはなっていない。

## 修正の優先順位

1. **今日の通知の再登録前の取り消しを省く。** 同じ `today-overview-reminder` 識別子で新しい要求を追加すれば既存の予約は置換されるため、現在の事前取り消しは不要。[Appleのidentifier仕様](https://developer.apple.com/documentation/usernotifications/unnotificationrequest/identifier)で確認した。通知を無効にする際の取り消しは引き続き必要。
2. **OSへの通知操作を同期のストア初期化から外す。** 初回表示をOSサービスの応答に依存させない。取り消し・追加の順序と、すでに実装されている世代チェックを維持して専用の直列処理に寄せる。`@MainActor`内の `_Concurrency.Task { ... }` へ囲むだけではメインスレッドから離れない。
3. **起動時の重複した再登録をまとめる。** 現在はストア初期化、Appの `onAppear`、`.active` への変化で今日の通知を再登録する。日付変更・予定変更・設定変更による必要な更新を保ち、同じ内容の起動要求を集約する。
4. 修正後は同じ実機で再計測し、初回描画に加えロゴ解除・操作可能になる時刻も比較する。通知の有効・無効、時刻・本文変更、日付変更、繰り返し予定の通知補充を回帰確認する。

## 2026年10月30日の修正

- 通知の再登録をストアの同期初期化とAppの `onAppear` から外し、ロゴの終了・アクティブ化・必要なロック解除後に開始する。ロゴの裏で完了した外部カレンダー取得は保存・表示へ反映し、通知は起動後に最新の内容を使って照合する。
- OSの通知操作を専用の直列キューへ移した。既存予約を取得し、識別子・内容・トリガーが同じ予約は維持する。キューが空になったら取得結果を破棄し、次回はOSの状態を取得し直すため、アプリの再起動や予約の消失後も補充できる。
- 日記・予定一覧の通知を追加する前の取り消しを省いた。内部予定・繰り返し予定・外部予定も、変更がある予約は同じ識別子で置換し、不要になった予約だけを削除する。
- 非同期の通知取得・登録は完了まで順序を維持し、古い予定の処理が新しい通知を削除しないよう世代チェックを保持する。登録エラーは成功として記憶せず、次の要求で再試行できる。
- 上記の実機の数値は修正前の記録。修正後の実機の短縮時間としては扱わない。
