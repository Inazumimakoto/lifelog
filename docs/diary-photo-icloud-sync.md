# 日記写真のiCloud保存

関連要件: `docs/requirements.md` §4.4 日記、§4.9 設定、§6 非機能要件。

## 利用者の操作と保存方針

設定の「日記の写真とiCloud」から「すべての写真をiCloudに同期」を押すと、既存の日記写真をまとめてアップロードする。以後に追加した日記写真も同期対象になる。最初の操作前はクラウド同期を開始せず、写真は端末に残す。

保存方法は次の2種類とする。

| 設定 | 高画質版 | サムネイル |
| --- | --- | --- |
| 端末容量を節約 | iCloudへの保存成功と同期情報の永続化を確認した後、端末のファイルを解放する。写真を開いた間だけ取得する。 | 全写真分を端末の永続領域に残す。 |
| すべて端末にも保持 | iCloudと端末の両方に保持する。クラウドだけにある写真はダウンロードする。 | 全写真分を端末の永続領域に残す。 |

初期選択は「端末容量を節約」。モードの選択だけでは初回同期を開始しない。未同期の写真はどちらの設定でも端末から解放しない。高画質版を追加で再圧縮する旧「ストレージ最適化」UIは置き換える。

カレンダーと一覧には端末のサムネイルを表示する。代表写真の変更は、保存済みの全写真のサムネイルから選べる。写真を拡大したときはサムネイルを先に表示し、高画質版の読み込み中表示、失敗時の再試行を提供する。未取得の高画質版はオフラインでは閲覧できない。

同期済み・未同期の写真数、同期処理の進捗、エラー、再試行を設定画面に表示する。通信やiCloudの空き容量等の問題があっても、未同期のローカル写真は維持する。中断後はアプリ起動・復帰などの再試行機会に続きから処理する。アプリが終了したままでのバックグラウンド完了は保証しない。

日記の添付写真を削除した場合は、日記専用のクラウドコピーも削除対象にする。取り消し期間やクラウドのゴミ箱は設けない。オフライン等で削除できない場合は、永続的な削除待ち情報を保持して次回再試行する。写真アプリの元写真は変更・削除しない。ローカル容量を解放する操作は、添付写真の削除とは別の処理として扱う。

## アカウントと容量

- iPhoneに設定済みのiCloudアカウントを使い、アプリ独自のログイン画面は追加しない。
- 手紙共有のFirebase認証とは独立した機能とする。
- 写真は利用者のCloudKit private databaseに保存する。iCloud写真とは独立したコピーなので、利用者のiCloud容量を別途使用する。
- 保存元のiCloudアカウントと現在のアカウントが異なる場合は処理を中断し、元のアカウントに戻す案内を表示する。

## ファイルとCloudKit

既存の写真ファイル名・日記の`photoPaths`を維持する。写真単位のCloudKitレコードIDは同じファイル名から決定するため、中断したアップロードを再送しても別の写真レコードを増やさない。

| 項目 | 保存先・形式 |
| --- | --- |
| 高画質版の端末ファイル | 既存の`Documents/DiaryPhotos/` |
| サムネイル | `DiaryPhotoFiles`管理の写真フォルダ内の永続サブフォルダ |
| 同期情報・削除待ち情報 | `Application Support/DiaryPhotoSync/manifest.json` |
| CloudKit container | `iCloud.com.inazumimakoto.lifelog` |
| データベース / zone | private database / default zone |
| Record type | `DiaryPhoto` |
| Record name | `diary-photo-` + 既存写真ファイル名 |
| フィールド | `photo`: CKAsset、`thumbnail`: CKAsset、`filename`: String |

アップロード前にサムネイルを作成し、サムネイルと高画質版を同じレコードに保存する。CloudKitの成功応答だけでなく、ローカルの同期情報の保存にも成功するまで高画質版は解放しない。同期情報を読み込めない場合は、写真の解放・クラウド操作を進めない。クラウドだけにある写真を「ローカルの欠損ファイル」として日記から除去しない。

写真同期の追加を契機として、SwiftDataの全データ同期を暗黙に有効にしない。日記データベースは明示的に`cloudKitDatabase: .none`とする。この機能にSwiftDataのスキーマ移行はない。サムネイルと同期情報は通常のiOSバックアップ対象に置く。

## 機種変更の範囲

クイックスタートやiOSのバックアップからの移行で、日記データベース、サムネイル、同期情報、設定を一緒に引き継ぐ想定とする。移行後は同じiCloudアカウントを使い、同期情報が参照する高画質版を取得する。移行方法は[Appleの案内](https://support.apple.com/en-ie/119967)に従う。

これは写真ファイルのクラウド保存機能であり、別端末への新規インストールだけで日記全体を復元したり、複数端末の日記編集を同期したりする機能ではない。端末移行で必要なローカルデータまで復元されたことは実機で確認する。

## 配布前のCloudKit設定

1. Apple Developerの対象App IDでiCloud / CloudKitを有効にし、`iCloud.com.inazumimakoto.lifelog`を関連付ける。XcodeのSigning & Capabilitiesと署名用プロファイルに同じcontainerを反映する。
2. 開発環境の実機で、`DiaryPhoto`レコードと上記3フィールドを作成し、アップロード・取得・削除を確認する。
3. [Appleのスキーマ配布手順](https://developer.apple.com/documentation/cloudkit/deploying-an-icloud-container-s-schema)に従い、CloudKit ConsoleからスキーマをProductionへ反映する。開発環境での成功だけではTestFlight / App Store環境の動作確認にならない。
4. Productionを使用する配布ビルドで、同じ操作とiCloudアカウント・容量不足時の挙動を確認する。

リポジトリ上のentitlementやコードの追加だけでは、Developer Portalのcontainer関連付けやProductionスキーマの反映は完了しない。

## 検証項目

- 既存写真をまとめて同期でき、容量節約時も全サムネイルと代表写真の変更が利用できる。
- アップロード失敗・同期情報の保存失敗・通信断では未同期の高画質版を削除しない。
- 中断したアップロード・削除が再起動後に再試行され、削除済み写真が復活しない。
- 「すべて端末にも保持」への変更で高画質版を再取得し、再度の容量節約で同期済み高画質版だけを解放する。
- iCloudサインアウト、異なるiCloudアカウント、容量不足、オフラインから回復できる。
- 同期済み写真のローカルファイルがない状態でも日記の参照が保持され、拡大表示で取得できる。
- クイックスタート / バックアップ復元後、同じ日記・サムネイル・同期情報から高画質版を取得できる。
- 設定画面・写真ビューア・エラー文言は`ja` / `en` / `ko` / `zh-Hans` / `zh-Hant`の5言語で表示する。利用者が作成した文章や写真名は翻訳しない。
- スクリーンショット用デモ・プレビュー・通常の単体テストから実際のクラウドへの操作を行わない。注入したテスト用バックエンドで状態遷移を検証する。

自動テストとシミュレーターのビルドはローカルの状態遷移・コンパイルを検証する。実アカウントでのアップロード、Productionスキーマ、署名プロファイル、機種変更の実機検証は別途必要。

## 実装時の検証結果（2026-09-26）

- iPhone 17 Pro / iOS 26.1 Simulatorで、追加19件を含むXCTest全58件が成功（失敗・スキップなし）。テスト用ホストは署名を有効にして実行した。
- 最終修正後に写真関連の19件を再実行し、すべて成功した。
- iOS Simulatorでビルド・起動に成功。日本語の設定画面で保存方法の2択、容量表示、同期件数、一括同期ボタンの表示を確認した。[確認時の画面](screenshots/diary-photo-icloud-settings-ja.jpg)はクラウド操作を無効にしたデモ環境のため、写真数は0件。
- `xcodebuild -project lifelog.xcodeproj -scheme lifelog -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO`で実機向けビルドに成功。これは署名や実機通信の検証を含まない。
- 追加した`photoStorage.*`の36キーが、5言語すべてに翻訳を持つことを検査した。
- この作業環境にはCloudKit管理用の認証情報がないため、Apple Developer側の設定変更やProductionへのスキーマ反映は実施していない。実アカウントとの同期・削除、および機種変更の実機検証も未実施。

## CloudKit Console設定の実施結果（2026-09-26、上記検証後）

利用者がCloudKit Consoleへログインした後、次を実施した。

- 対象チームの`iCloud.com.inazumimakoto.lifelog`が登録済みであることを確認。
- Developmentに`DiaryPhoto`を作成し、`filename: String`、`photo: Asset`、`thumbnail: Asset`を保存。
- `DiaryPhoto`はPrivate Databaseだけで使用するため、自動付与されたPublic Databaseの`_world` / `_icloud` / `_creator`権限を外した。既存の`Users`の権限は維持。
- 本番との差分が上記レコード型の追加だけであることを確認し、Productionへスキーマを反映。Production画面でも3フィールドを確認した。[反映後の画面](screenshots/diary-photo-cloudkit-production.png)。写真レコード自体はアップロードしていない。
- `xcodebuild -project lifelog.xcodeproj -scheme lifelog -destination 'generic/platform=iOS' -allowProvisioningUpdates build`が署名を含め成功。生成アプリのCloudKit entitlementと、埋め込まれた開発用プロファイルの対象container許可を確認した。

これで保存先・スキーマの準備は完了。App Storeへのアップロード・公開は行っていない。実アカウントでのアップロード・取得・削除、容量解放、TestFlightの配布署名、機種変更の実機確認は引き続き未実施で、一般公開前に確認する。

### 次の実機確認

この変更を含むTestFlightビルドで、まず「すべて端末にも保持」を選び、写真を同期できることを確認する。その後「端末容量を節約」に切り替え、全サムネイルが残ること、写真を拡大して再取得できること、添付を削除するとクラウドのコピーも消えることを確認する。削除テストには不要なテスト写真を使う。

DevelopmentとProductionは別の写真保存領域であり、スキーマ配布は写真レコードをコピーしない。現在の同期台帳は環境を区別しないため、同じインストールのまま開発版からTestFlight版へ移るテストでは、開発版で写真の容量解放を行わない。すでに解放した場合は同じ開発版・同じiCloudアカウントで「すべて端末にも保持」に戻し、取得完了を確認してから移る。通常利用の確認には最初からTestFlightのProduction環境を使う。
